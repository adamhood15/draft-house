# Contributing

Draft House is a small private project, but the workflow is deliberate: work is done by
role-scoped agents reading narrow slices of the documentation, and the conventions below exist to
keep that structure intact. See [AGENTS.md](AGENTS.md) for the role system itself.

## Before you start

1. **Know your role.** Open `agents/<ROLE>.md` and read its Read Map, Hard Constraints, and Out of
   Scope table. If you were not assigned one, you are the Orchestrator: route the work rather than
   doing it.
2. **Read only what your map names.** If you believe you need a document outside it, do not read
   it — report it as a blocker. See [AGENTS.md](AGENTS.md) for the read-map contract.
3. **Set up locally.** [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md) covers environment variables,
   the local database, and seeding test data from Sleeper.

```bash
npm install
npm run dev
```

## Branches

- Branch off `main`. Never commit directly to `main`.
- Name branches `<area>/<kebab-case-description>`, where the area is the owning role, lowercased:
  `trades/counter-offer-validation`, `security/picks-rls`, `docs/role-scoped-restructure`.
- One branch per handoff. If a change spans two roles, that is two branches in sequence, not one
  branch doing both.

## Commits

Match the existing log — imperative mood, sentence case, no trailing period:

```
Add invite/team-claiming flow, and remember Sleeper identity across imports
Fix seed script's scoring_format/positions fields to match Sleeper's real API
Move ARCHITECTURE.md into docs/
```

- Subject line under ~72 characters, saying what the commit does.
- Body explains *why*, and any decision a reader would otherwise have to reverse-engineer. Wrap at
  ~80 characters.
- Keep mechanical changes separate from substantive ones. A file move or a verbatim extraction
  belongs in its own commit so the real diff stays readable.
- Do not commit secrets. Keys come from the environment — see
  [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md).
- `AGENTS.md` contains a `nextjs-agent-rules` block regenerated by `next dev`. Do not delete it;
  removing it only recreates an uncommitted change. If it reappears unrelated to your work, commit
  it separately.

## Verifying a change

Run these before you push. Both currently pass clean on `main`:

```bash
npx tsc --noEmit      # typecheck
npm run lint          # eslint
npm run build         # production build
```

"Done" means the checks are green **and you ran them**, with the literal output in your handoff or
PR description. If a step failed or was skipped, say so plainly rather than omitting it. A
user-facing flow additionally needs exercising end to end in the browser — two windows side by
side for anything real-time.

### Tests

[AGENTS.md](AGENTS.md) makes TDD mandatory: failing test first, implement, verify. **That rule is
currently unenforceable — this repository has no test runner and no test files.** There is no
`npm test` script, and no framework in `devDependencies`.

Until a runner is installed, do not report a change as tested, and do not write a handoff claiming
green tests. State `"tests": "not run — no runner installed"` and rely on typecheck, lint, build,
and manual exercise. Choosing and wiring up the runner is its own piece of work; raise it rather
than quietly inventing a local setup that no one else shares.

## Pull requests

A PR description contains:

- **What changed and why**, in prose. Not a file list — the diff already has that.
- **The handoff block** for your role, in the JSON shape defined in [AGENTS.md](AGENTS.md).
- **Literal verification output** for every check you ran, and an explicit note for any you did not.
- **Anything out of scope you noticed but did not fix.** Report it; do not fix it silently.

Keep PRs to one role's ownership. A PR touching files outside your role's area is a finding in
review even when the code is good.

## Documentation changes

Documentation is owned by `DOCS_STEWARD` — see [agents/DOCS_STEWARD.md](agents/DOCS_STEWARD.md).
The rules that matter most:

- **One fact, one home.** When two documents describe the same behaviour, one is authoritative and
  the other links to it. Two live copies is how two agents build two different behaviours.
- **Splits are verbatim.** Move content byte-for-byte in one commit; edit it in another, so the two
  are separately reviewable.
- **Do not resolve a contradiction by picking whichever version you read first.** Establish which
  is right from the code, the migrations, or the author. Some documents describe intended state for
  features that do not exist yet, and the code is not always the authority.
- **Never mark something as existing that does not**, or as TBD when it ships. Check the
  filesystem.
- If you move or rename a section, fix the inbound links *and their link text*. Broken anchors fail
  silently: the reader follows the link, finds nothing, and continues without the context.

`supabase/migrations/` outranks the prose in [docs/DATABASE.md](docs/DATABASE.md) and
[docs/SECURITY.md](docs/SECURITY.md). When they disagree, the migration is what shipped.

## Reporting a problem you cannot resolve

Blockers are a valid outcome. A `partial` or `blocked` handoff that names the obstacle is more
useful than a `complete` one that guessed. This applies to contradictions in the docs, missing
tooling, and decisions that are genuinely the owner's to make.
